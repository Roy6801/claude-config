# Checkpoint, walkthrough, ship

Runs when the last planned commit lands (`pair commit` moves the PR to its checkpoint) and `pair next` says `checkpoint`. Each step finishes before the next one starts, and every fix lands as its own commit through `pair commit --title`, so the checkpoint stays in the record. Heavy reviews run in agents; the main thread relays findings and asks.

When `pair next` says `ship` (the PR was built in an earlier chat), run only green (step 2), then steps 4 to 7.

1. **Review.** Run the `review` skill in `slice` scope on the PR's diff. It runs `/simplify` (accepted changes land as extra commits; run `pair check` first and name `/simplify` in the why), then both `reviewer` passes (thermo and correctness) with the conventions bundle the plan used, then AC conformance. Give the findings to the user grouped as fix now, follow-up, or rejected with reason. Accepted fixes become extra commits; follow-ups go to the ticket or issue, or a later PR, only with approval.
2. **Green.** Run `pair green`. It needs a clean tree and changes no SHAs. On failure it aborts the rebase and reports the first failing commit with the last 20 lines of the check. If the failing commit is the latest one, fix it with a new commit and rerun. If an earlier commit fails while later ones pass, the history has a commit that is not green: tell the user which commit and why, and ask how to proceed. Repairing it means rewriting the branch, which needs a force push; this skill never does that, so the user either accepts the note in the walkthrough or rewrites the branch themselves.
3. **QA.** Run the `qa` skill scoped to the PR's ACs. Report a verdict per AC (pass, fail with exact reproduction, or uncertain), with a GIF where the AC has UI. A failure goes back to the build loop as a new commit.
4. **Ask.** One message: the checkpoint result in two or three sentences, the PR's "How you can check it yourself" steps from the plan, and the question "Walk through the PR now?".
5. **Walkthrough.** Run `pair walk --slice <n>` and write every commit in one message, in order: 2 or 3 plain sentences on what it does for users and why, plus a small snippet where it helps. Deviations from the plan come first. Answer follow-up questions from the diff, not from memory.
6. **OK.** Wait for the user's one OK on the whole PR (their own test included). Findings from their test become new commits, then a short walkthrough of just those.
7. **Ship.** The user's OK after the walkthrough (or their ask to create the PR) is the go-ahead: run `/ship`, which pushes and opens the draft without asking again; only the attachments go to the user for review first. Then run `pair slice ship <n> --pr <number>`: it marks the PR shipped, updates roadmap.md and prints the next PR with its starter. Close with the handoff question from `SKILL.md`: "PR <n> is open as draft #<number>. Hand off to a fresh chat for PR <n+1>, <name>?"

Offer a private artifact page of the checkpoint when the user wants to share it: the check steps, the walkthrough, and an AC → commit → test → evidence table.
