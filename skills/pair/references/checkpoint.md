# Slice checkpoint

Run when the slice is in `checkpoint`, which `pair commit` sets when the last planned commit lands. Each step finishes before the next one starts, and every fix lands as its own commit through `pair commit`, so the checkpoint itself stays in the record. Heavy reviews run in agents; the main thread relays findings and asks.

1. **Review.** Run the `review` skill in `slice` scope on the slice diff. It runs `/simplify` (accepted changes land as extra commits through `pair commit --title "<conventional title>"`, naming `/simplify` in the why; run `pair check` first), then the `reviewer` agent with the thermo rubric and the conventions bundle the plan used, then AC conformance. Give the findings to the user, grouped as fix now, follow-up, or rejected with reason. Accepted fixes become extra commits; follow-ups go to the ticket or the next slice only with approval.
2. **Green.** Run `pair green`. It needs a clean tree and changes no SHAs. On failure it aborts the rebase and reports the first failing commit with the last 20 lines of the check. If the failing commit is the latest one, fix it with a new commit and rerun. If an earlier commit fails while later ones pass, the history has a commit that is not green: tell the user which commit and why, and ask how to proceed. Repairing it means rewriting the branch, which needs a force push; this skill never does that, so the user either accepts the note in the walkthrough or rewrites the branch themselves.
3. **User test.** Give the user the slice's `test_script` exactly as planned, plus how to run the app if it is not obvious. Wait for their result. A failure goes back to section 3 of the skill as a new commit.
4. **QA.** Run the `qa` skill scoped to the slice's ACs. Report a verdict per AC (pass, fail with exact reproduction, or uncertain), with a GIF where the AC has UI.
5. **Walkthrough.** Run `pair walk --slice <n>` and relay it: the deviations summary first, then commit by commit (title, why, the per-file notes, the stat, the key hunks). Ask whether the user wants to pause between commits; when they do, wait for their go-ahead before the next one. Answer questions from the diff, not from memory.
6. **User OK.** On the user's explicit OK: `pair slice done <n>` (it refuses while any commit is todo; never pass `--force` without the user's say-so), then `bun $CLAUDE_CONFIG_DIR/bin/work.ts step - <step> done` when the slice completes a roadmap step, and log notable outcomes with `work.ts decide`. When the slice has a ticket or issue, draft the update (status and a short summary with the PR link) and apply it only with approval: through the `ticket` skill for Linear, `gh issue comment` for a GitHub issue.

Then offer the `handoff` skill: the next slice starts best in a fresh session, and `pair resume` picks it up from `pair.json`.

Offer a private artifact page for the checkpoint when the user wants to share it: the test script, the walkthrough, and an AC → commit → test → evidence table.
